# Permanent previews with memorable URLs — design

Status: proposed (implementation not yet included).
Scope: authenticated web UI and internal session-protected HTTP transport; existing MCP contracts unchanged.

## User story
As a signed-in owner, I can promote a READY, unexpired temporary preview to a permanent publication and choose a memorable hostname such as `tulldeklaration.preview.apphome.one`. The content remains available until I delete or explicitly unpublish it. I can update it under the same URL and export it with the existing ZIP action.

## Architecture decisions
1. Keep the generated `p-<hex>` id and on-disk `previews/<id>/current` storage layout. The ID remains immutable and is the canonical storage identity.
2. Add an explicit `publication_mode` (TEMPORARY/PERMANENT) and optional unique `slug` to the existing `previews` table. For permanent previews expiry is not applicable; migrate `expires_at` to nullable and constrain its nullability by mode. Avoid fake far-future timestamps.
3. Keep the existing autogenerated preview-ID hostname working as an alias for permanent previews, so existing links do not break. In addition, resolve an exact one-label slug subdomain, then fetch a READY permanent preview by indexed slug. Namespaces must be disjoint (reject reserved `p-<32 lowercase hex>` id patterns).
4. Use the existing wildcard TLS and reverse proxy; no new DNS records per preview.
5. Promote through an authenticated, owner-scoped UI action and an internal session-authenticated endpoint. Preserve the existing `404` non-disclosure policy.
6. Use a database uniqueness constraint and conditional UPDATE to atomically reserve slugs. Never use a check-then-insert alone.
7. Cleanup and reconciliation must not remove READY permanent previews. `claimExpired` must filter TEMPORARY; serving rules must evaluate mode before expiry. Include quota-aware permanent counts.
8. Never alter the existing MCP tool schemas for create/list/get/update/extend/delete in this phase. Extend/update an existing permanent publication through normal update; extension of a permanent publication should be rejected with a specific validation code.
9. Permanent means no TTL eviction, not an SLA or a backup guarantee. Recommend volume and database backup/restore testing before production enablement.

## Suggested migration
A new additive numbered migration following the current highest number:
- Create enum or text CHECK for publication_mode, default TEMPORARY.
- Add slug nullable, enforce lowercase DNS-label format, length 3–40, and reserved-name policy in application validation. Unique index on slug WHERE slug IS NOT NULL.
- Drop NOT NULL on expires_at after accounting for current constraints. Add mode/expiry/slug consistency checks, with `TEMPORARY => expires_at not null and slug null` and `PERMANENT => expires_at null and slug not null`.
- Convert existing rows safely to TEMPORARY. Keep legacy hostname as immutable generated ID hostname.

## Slug validation
- ASCII lowercase `[a-z0-9]` with interior hyphens, 3–40 characters; normalize input to lowercase.
- Reject `www`, `api`, `auth`, `mcp`, `admin`, `login`, `health`, `ready`, `support`, `static`, `assets`, and `p-[a-f0-9]{32}`.
- Return a useful 409 if the name is already claimed; never reveal the owner.
- Do not transfer or recycle a slug silently: on deletion it may be released only after explicit user confirmation; document that external links will then stop working.

## Promotion flow
1. User clicks “Behåll permanent” on a READY preview.
2. UI proposes an editable slug and previews the final HTTPS URL.
3. Server validates session, owner, READY state, still-unexpired temporary state, available permanent quota, and atomic uniqueness.
4. In a transaction update mode, slug, and expires_at. No filesystem move or replication.
5. UI presents the permanent URL and retains actions Open, Update, Download ZIP, Delete. Disable Extend for permanent previews.
6. Requests to `<slug>.<preview-domain>` resolve to the existing static-site serving path by internal ID.

## Management decisions
- Version 1 is promotion-only; creating permanent publications directly or demoting them can come later.
- Permanent-preview default quota: configurable 10 per owner. Existing storage byte quotas still apply.
- Deleting a permanent publication must request explicit confirmation mentioning the memorable URL.
- If slug renaming is later supported, treat redirect persistence and name squatting as separate product decisions.

## Security, reliability and failure modes
- Reject unrecognized hosts and multi-level subdomains.
- Never treat user-controlled host strings as filesystem paths.
- Ensure canonical path validation before reading from storage.
- Resolve owner and slug only at the control-plane API, while slug-host serving is read-only and public, same as previews today.
- Preserve noindex, nosniff, MIME controls and cookie separation between control and preview domains.
- Handle promotion racing cleanup, deletion, update and expiry. Promotion must condition on READY, TEMPORARY and expiry > DB now(); cleanup claim must condition on TEMPORARY and expiry <= DB now(). Row-level update serialization prevents double transitions.
- Slug requests should 404 when the record is deleted or not READY.
- Backup persistent volume, DB and configuration; test restoration before advertising permanence.

## Required tests
1. Existing TTL cleanup unchanged for temporary previews.
2. Permanent READY previews survive cleanup and restart/reconciliation.
3. Promotion with unique slug succeeds and both old/generated and slug hostnames work.
4. Promotion of expired/deleted/another user's preview is rejected without leaking ownership.
5. Duplicate slugs and simultaneous promotions -> exactly one succeeds.
6. Invalid/reserved names and multi-level subdomains -> denied.
7. UI controls change by mode; Extend hidden/disabled on permanent preview.
8. Updating a permanent preview changes the content without changing either URL.
9. Existing ZIP export then upload remains functional.
10. Verify production wildcard TLS routing and backup/restore.

## Delivery slices
1. Database migration, model, repository, resolver, serving and cleanup coverage.
2. Owner-scoped promote endpoint and React UI.
3. Integration tests, E2E, documentation and deployment/backup checklist.
